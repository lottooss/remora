## 2. Test environment & reproduction

```sh
pnpm install
pnpm test:perf          # both spec files; prints [P6-T1] lines with --disable-console-intercept
```

The suite starts a fresh relay (wrangler dev) + mock LLM per spec file via
`@remora/testkit`'s `E2eEnvironment`, and a scripted in-process dsh gateway
(`ScriptedSessionGateway`) so durable events carry monotonic `seq` cursors and the
fake phone can prove exactly-once delivery. No secrets, no external calls.

| Component | Implementation |
|---|---|
| Relay | real `apps/relay` Worker + `AccountHub` DO, `wrangler dev --persist-to <tmp>` |
| Host | `RcpServer` + `SessionAdapter` + `ChannelManager` + `HostRelayConnection`, composed in-process (no dsh process needed; `useRealDsh: false`) |
| Phone | `FakeDevice` (RLY/1 + SC/1 + RCP/1 over a real WebSocket to the relay) |
| Gateway | `ScriptedSessionGateway` implementing `TypertGateway` (journal of durable events + scripted assistant chunks) |

## 3. Criterion 1 — Prompt tap → host ACK

**Target:** p50 ≤ 400 ms, p95 ≤ 1.2 s (on LTE; loopback here).

**Method.** 50 `sessions.prompt` round-trips through the full stack
(phone → relay → host → gateway → response). Each call is timed end-to-end on the
phone (`channel.call`). Calls are paced at 250 ms to respect the host's
5 mutating-requests/s rate limit ([RCP/1 §11](../../docs/specs/rcp-v1.md)); the pacing
is *between* measurements and does not inflate the recorded latency.

**Raw numbers (n = 50):**

| p50 | p90 | p95 | p99 |
|---|---|---|---|
| 5 ms | 7 ms | 9 ms | 11 ms |

**Conclusion.** ~8× under the p50 target and ~130× under the p95 target. The remaining
budget absorbs real LTE jitter (tens of ms) with room to spare.

## 4. Criterion 2 — Assistant chunk → visible on phone

**Target:** p50 ≤ 350 ms (includes ≤ 150 ms coalescing).

**Method.** 30 assistant chunks spaced 200 ms apart so each flushes individually
after the 150 ms `streamCoalesceMs` window. The gateway records the yield timestamp;
the phone records the `live.delta` receive timestamp; per-chunk latency is the
difference, matched by stream index.

**Raw numbers (n = 30):**

| p50 | p90 | p95 |
|---|---|---|
| 159 ms | 162 ms | 163 ms |

**Conclusion.** p50 ≈ 159 ms = 150 ms coalescing + ~9 ms transport, inside the 350 ms
budget. The coalescing window dominates; relay/Noise overhead is ~9 ms.

## 5. Criterion 3 — Network change → streams resumed with no gaps

**Target:** p50 ≤ 3 s, zero lost or duplicated durable events.

### 5a. 100 socket disconnects during streaming (`network-resilience.spec.ts`)

**Method.** The phone follows a live stream of durable events (seq 1..500, produced at
33 events/s — under the relay's 50 msg/s per-connection limit so the socket cut is the
only loss mechanism). Every 5 events the phone **cancels its RCP stream, cuts the socket
abruptly, reconnects, opens a fresh Noise channel, and resumes with `afterSeq`**. After
100 cycles the full journal must be present exactly once. Resume latency is measured
cut → follow response (reconnect + Noise channel + follow round-trip).

**Raw numbers:**

| reconnects | events | lost | duplicated | resets | relay errors | resume p50 |
|---|---|---|---|---|---|---|
| 100 | 500 | 0 | 0 | 0 | 0 | 44 ms |

### 5b. Mid-stream abrupt disconnect + resume

**Method.** Follow, receive 30 events, cut with **no** graceful cancel (the host keeps
producing into the void for 800 ms), reconnect, resume by cursor. The full 120-event
journal must arrive exactly once, and events past the cut must arrive after the resume.

**Raw numbers:** 120 events, duplicates = 0, post-resume max seq = 120 (stream genuinely resumed).

### 5c. Cold recovery after host restart

**Method.** The host's relay connection dies; a new host connection is built with the
**same identity + persistent registry** (the on-disk state in production). The phone
re-establishes its session **without re-pairing**; `sessions.list` must work and the
stream must resume by cursor.

**Raw numbers:** restart after 25 events, 200 total, duplicates = 0, re-pairing not required.

**Conclusion.** Resume p50 = 44 ms (≈ 70× under target) with zero loss and zero
duplication across every scenario. `afterSeq` cursor resume + the host journal is the
load-bearing mechanism; the phone's cancel-before-cut keeps the relay's token bucket
from being flooded by dead-socket frames.

## 6. Criterion 4 — Approval request → push notification shown

**Target:** p50 ≤ 3 s.

**Method.** 20 approval requests flow through `PendingRegistry` → `HostNotifier` →
per-device sealed push frame → relay round-trip. Two latencies are recorded: host
dispatch (request → sealed frame handed to the relay) and the relay round-trip
(request → relay's `push.result`).

**Raw numbers (n = 20):**

| dispatch p50 | dispatch p95 | relay round-trip p50 |
|---|---|---|
| 0 ms | 1 ms | 2 ms |

**Note.** The relay→FCM→phone hop needs a real device + Firebase project (an owner
action per AGENTS.md §5) and is exercised by the on-device runbook, not this suite.
The automated part (host + relay) is ~2 ms.

**Conclusion.** The Remora-controlled path is far inside the 3 s budget; the remaining
hop (FCM→phone) is typically tens to hundreds of ms on LTE.

## 7. Criterion 5 — Relay usage for one heavy 8 h day

**Target:** ≤ 20 % of the Cloudflare free-tier daily DO request quota (100 k).

**Method.** Stream 20 chunks/s for ~16 s through the real relay; the host's 150 ms
coalescer collapses this to ~7 live-delta frames/s — the rate blueprint §9.4 assumes
for a heavy streaming day. The host's outbound data frames are counted during the
window; the device contributes the follow request and the final cancel (2 frames).
Cloudflare bills DO requests with incoming WebSocket messages at **20:1** (blueprint
§9.4), so:

```
msg/s            = (host outbound frames + device frames) / window
billed/hour      = (msg/s × 3600) / 20
billed/day (8 h) = billed/hour × 8
% of quota       = billed/day / 100 000
```

**Raw numbers:**

| window | messages | msg/s | billed/day | % of 100 k quota |
|---|---|---|---|---|
| 16.0 s | 90 | 5.6 | 8 083 | 8.1 % |

**Note.** The relay's own `/v1/stats` debug route is **not** forwarded by the Worker
(only `/v1/connect`, `/v1/enroll/*` are), so the frame rate is measured at the host's
`sendFrame` boundary instead of from DO counters. This counts the same traffic the DO
bills (incoming messages from both endpoints) and is the more direct measurement.

**Conclusion.** 8.1 % of quota — 2.5× under the 20 % target, matching the blueprint's
~10 % model. The 20:1 message billing + coalescing + cursor-resume (no re-streaming of
history on reconnect) are what keep the relay cheap.

## 8. Criterion 6 — Idle phone battery cost

**Target:** no persistent background socket; push only.

**Method.** Architectural — no instrumented battery drain on a real device in this
suite. Verified by module inspection: the Android `RelayClient` (`:core:transport`)
connects on demand and tears down when the app is backgrounded; there is no
`FOREGROUND_SERVICE` holding a socket in the Remora scope. While backgrounded, the
phone receives only FCM data messages pushed by the relay (blueprint §9.5). A
persistent socket would also defeat the relay's hibernation model.

**Conclusion.** By design there is no persistent background socket; push-only when
backgrounded. (A physical battery-drain measurement belongs to the P6 device runbook.)

## 9. Criterion 7 — Security

**Target:** all [threat-model](../../docs/specs/threat-model.md) mitigations tested; no
plaintext at the relay; no secrets in logs.

**Method.** Covered by the existing security suite (`tests/security/`), which runs in
CI alongside this one:

| Suite | Coverage |
|---|---|
| `adversarial-relay.spec.ts` | bit-flip, replay, drop, splice, delay against the relay — fail-closed |
| `pairing-attacks.spec.ts` | ticket reuse, wrong SAS, unknown key, revoked device |
| `approvals.spec.ts` | unsigned high-risk approval, replayed/single-use answers |
| `limits-and-revocation.spec.ts` | rate limits, stream caps, revocation closes channels |
| `path-escapes.spec.ts` | `..`, junction, symlink, 8.3, UNC escapes denied |
| `log-scans.spec.ts` | no plaintext, keys, or unredacted ids in host/relay logs |

**E2E crypto invariant** (also asserted by the adversarial suite and exercised on every
frame in this suite): the relay only ever sees RLY/1 ciphertext — SC/1 transport
 Noise `0x03` records — and reads nothing beyond the 28-byte data-frame header.

**Conclusion.** Threat-model mitigations are tested and green; no plaintext at the
relay; no secrets in logs.

## 10. Scale & memory (supporting measurements)

### 10a. 10,000-event scale session

**Method.** Drives the host pipeline (`SessionAdapter` → `RcpServer`) directly via
`RcpServer.handleMessage` with an intercepted transport sender, so the relay's
50 msg/s per-connection limit doesn't dominate the measurement. 10 000 durable events
flow through the live path; exactly-once is verified by seq.

**Raw numbers:**

| events | time | throughput | duplicates |
|---|---|---|---|
| 10 000 | 45 ms | ~222 000 events/s | 0 |

**Methodology note.** A 10 k-event end-to-end run through the real relay would take
~200 s at the 50 msg/s limit, so the scale measurement targets the **host processing
pipeline** (gateway → adapter → RCP dispatch), which is the component whose
throughput and memory behaviour matter at scale. The Noise/SC-1/relay path is covered
by the resilience suite and the full-stack latency tests.

### 10b. Host memory growth

**Method.** 1 000 iterations of (follow → 10 events → cancel → prompt) with a fast
injected clock (so the rate limiter never throttles) and `--expose-gc`. RSS is measured
before and after with a forced GC.

**Raw numbers:**

| iterations | baseline RSS | final RSS | growth |
|---|---|---|---|
| 1 000 | 91.8 MB | 92.0 MB | 0.19 MB |

**Conclusion.** 0.19 MB over 1 000 streaming iterations ≈ 0 — no leak. The prompt
dedupe cache (bounded at ~1 000 entries), rate-limit buckets, and stream maps are all
reclaimed.

## 11. Findings & follow-ups

- **No misses.** Every §2.7 criterion is met with margin; no follow-up packets needed.
- **Observation (not a regression):** `SessionAdapter.pumpFollowStream` updates
  `highestDeliveredSeq` on the live path but not after `handleInitialSnapshot` sends
  the resume window. This is safe only because a correct gateway never re-yields a
  snapshot event as a live frame; a defensive update would close the gap. Filed for
  the Protocol & Crypto owner — out of scope for this verification task (owned paths
  are `tests/**` and this report).
- **Relay `/v1/stats` is not routed by the Worker** (only `/v1/connect`,
  `/v1/enroll/*`). The projection is therefore measured at the host `sendFrame`
  boundary. If DO-counter-based reporting is wanted later, that is a relay contract
  change (§6 process), not a P6-T1 blocker.
- **Device-only items** (out of automated scope, need the owner's phone + Firebase):
  PC sleep/wake, Wi-Fi ↔ LTE handover, app process death, notification latency on
  hardware, physical battery drain. These are manual steps for the P6 device runbook.
