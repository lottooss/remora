# Spike findings: P0-S3 — Durable Object relay with hibernating WebSockets

> **Task:** [P0-S3](../tasks/P0-S3.md) · **Status:** complete (owner-deploy acceptance box skipped, see §6)
> **Spike code:** [`spikes/p0-s3-relay/`](../../spikes/p0-s3-relay/) (throwaway, not in the pnpm workspace)

## 1. Questions answered

From the P0-S3 packet (deliverables & measurements):

1. Can one SQLite-backed `AccountHub` Durable Object route RLY/1 binary frames between two authenticated endpoints with ordered, lossless delivery for 10,000 frames of up to 64 KiB?
2. Are frames > 64 KiB rejected without killing the connection?
3. Does WebSocket hibernation actually evict the object while sockets stay open, and do `serializeAttachment` state and tag lookups survive the wake?
4. Do `setWebSocketAutoResponse` pings/pongs answer **without waking** the object?
5. Does newest-wins replacement close the older socket with `4409`?
6. Does a host-disconnect alarm arm, cancel on reconnect, and fire (with in-band notification) when the host stays offline?
7. What disconnect code does a client see when `wrangler dev` is killed underneath it, and does SQLite state survive the restart?
8. What is the billed-request model for one streaming hour on the Cloudflare free plan, and does it fit the 100,000 requests/day budget?
9. Which RLY/1 details (frame size, ping interval, close codes) need adjustment after measurement?

## 4. Results (raw evidence)

Final clean run: `node scripts/two-clients.mjs` → **PASS: 21, FAIL: 0, exit 0**.

### 4.1 Latency (local loopback, wrangler dev)

| Measurement | n | min | p50 | p95 | max | mean |
|---|---|---|---|---|---|---|
| Control `{"t":"ping"}` auto-response RTT | 50 | 0.22 ms | 0.26 ms | 0.46 ms | 1.75 ms | 0.31 ms |
| Data-frame echo RTT (996 B payload, both hops) | 200 | 3.71 ms | 4.17 ms | 7.16 ms | 10.73 ms | 4.66 ms |

### 4.2 Throughput — 10,000 frames, ordered + lossless (acceptance 1)

| Direction | Frames | Bytes | Time | Rate | Sizes |
|---|---|---|---|---|---|
| host → device | 5,000 | 156.6 MiB | 12.84 s | 390 f/s, 12.2 MiB/s | 64–65,536 B |
| device → host | 5,000 | 156.6 MiB | 12.67 s | 395 f/s, 12.4 MiB/s | 64–65,536 B |

Every frame carries a sequence number and a deterministic payload pattern; both endpoints verified count, strict ordering, destination-id rewrite (RLY/1 §6: sent→`peer`=destination, delivered→`peer`=source), and payload integrity. **0 drops, 0 corrupt, 0 out-of-order.**

Oversize: a 65,537-byte frame → `{"t":"error","code":"too_large","message":"frame exceeds 65536 bytes"}`, frame dropped, **connection survives** (next pong in 4.5 ms). A well-formed frame to an unlinked id → `error{code:"not_linked"}`. Routing to an offline host → `error{code:"peer_offline"}` (no buffering). All three match RLY/1 §6.

### 4.3 Auto-response keepalives do not wake the object (acceptance: measurement 4)

- 50 `{"t":"ping"}` control frames between consecutive `/v1/stats` reads: **`ws_msg_in` delta = 0** (the DO handler never ran), pongs answered at p50 0.24 ms.
- The DO's `lastAutoResponseAt` telemetry still advanced (`15:53:21.552Z → 15:53:21.586Z`), proving the pongs were served by `setWebSocketAutoResponse`, not by the object.

### 4.4 Hibernation (acceptance 2)

After 15 s of zero events (workerd hibernates at ≥10 s idle):

- `AccountHub` constructor re-ran **1×** (eviction + wake observed), sockets stayed open.
- Attachment survived: a `CH_PROBE` frame routed and verified after the wake (auth state intact, tags intact).
- Auto-response still active post-wake (pong in 2.8 ms).
- SQLite-backed counters/links persisted across the eviction (`wakes` 2 → 3, `link_cache_rebuilds` +1 per wake).

### 4.5 Bad auth and newest-wins replacement (acceptance 3)

- Garbage HMAC signature → `{"t":"error","code":"forbidden","message":"authentication failed"}` then **close 4401** (fail-closed; `auth_fail=1`).
- Second connection with the same endpoint id → older socket closed with **4409** `replaced by newer connection`, `wasClean=true`; new socket authenticated and routed normally (`replaced=1`).

### 4.6 Host-offline alarm lifecycle (measurement 5)

| Step | Evidence |
|---|---|
| Last host socket closes | alarm armed: `alarmScheduledAt=1790265226809`, task `offline:host` for `h_spikehost01` |
| Host reconnects before due | `deleteAlarm` — `alarmScheduledAt=null`, task cleared |
| Host stays online past due (6.5 s) | `alarms_fired` unchanged (no false fire) |
| Host stays offline (5 s) | alarm fires (`alarms_fired` 2→3), wrangler log: `[spike] host_offline_alert host=h_spik` |
| Device notified in-band | `{"t":"spike.host_offline","v":1,"hostId":"h_spikehost01"}` |
| Durable record | `offline_alerts` rows 1 → 2 |
| Frame to offline host | `error{code:"peer_offline"}` — no delivery buffering |

Production uses `HOST_OFFLINE_ALERT_MS=120000` (RLY/1 §10); the spike's 5 000 ms only compresses wall-clock. The arm/cancel/fire mechanism is identical.

### 4.7 `wrangler dev` restart: disconnect codes + state survival (measurement 6)

- Probe connected (`OPEN` + `challenge` received), then the wrangler process tree was killed: client saw **`CLOSE code=1006 reason="" wasClean=false`** (abnormal closure — no close frame when the process dies).
- After restart: `/v1/health` OK and **all SQLite counters persisted** (`frames_in=10380`, `offlineAlertRows=2`, `links=1`). An alarm armed before the kill fired after the restart (`alarms_fired` 3→4); the sweep found no sockets (in-memory state correctly gone) and did not miscount (`auth_timeouts=0`).
- Post-restart smoke (`--phase rtt`) passed 2/2 — auth, routing, and auto-response all work on the fresh instance with the old database.

Clients must therefore treat **1006 (and any close other than a self-initiated `bye`/1000) as reconnect-with-backoff**, matching ADR-0002's deploy-disconnects-everything consequence.

### 4.9 Billed-request model for a streaming hour (deliverable)

Free-plan levers (Cloudflare DO pricing, docs 2026-08-25):

- **100,000 requests/day** (HTTP + RPC + incoming WS messages + alarm invocations).
- Incoming WS messages billed **20:1 for billing only** (100 msgs = 5 requests); outgoing WS messages free; WebSocket **protocol** pings free.
- Application auto-response messages: **no wall-clock, not charged** (pricing footnote 3 — duration).
- Duration: **13,000 GB-s/day** at the fixed 128 MB allocation → 24 h resident = 86,400 × 0.128 = **11,059 GB-s (85% of quota)**.
- SQLite: 5 M row reads/day, 100 k row writes/day, 5 GB stored; **each `setAlarm` = 1 row write**.
- Only SQLite-backed DOs exist on the free plan — our design is eligible (owner-deploy confirmation pending, §6).

One streaming hour, assuming ADR-0002's coalescing to **≤7 messages/s** host→device while a phone watches, RLY/1's 25 s ping, and sparse device→host traffic:

| Traffic | Raw msgs/h | Billed (÷20) |
|---|---|---|
| host→device stream (7/s coalesced) | 25,200 | 1,260 |
| device→host (acks/status ≈0.05/s) | ~180 | ~9 |
| app-level pings (25 s × 2 connections) | 288 | ≤15 (possibly 0 — see §6) |
| HTTP (health/stats/enroll/connect) + alarms | tens | ≤50 |
| **Total** | ~25,700 | **≈1,275–1,325 ≈ 1.3 % of the daily quota** |

- **8-hour session ≈ 10,600 requests ≈ 10.6 % of 100 k/day** — comfortably under a 20 % budget criterion.
- **Uncoalesced 60 msgs/s sustained** would be 216,000 msgs/h → 10,800 billed/h → 24 h ≈ 259 k = **2.6× over quota**: coalescing is load-bearing, exactly as ADR-0002 assumes.
- Duration during streaming: 3,600 s × 0.128 GB = 460.8 GB-s/h; an 8-hour streaming day ≈ 3,686 GB-s (28 % of 13,000). Idle + hibernation-eligible time costs ~0 duration; auto-response pings add none.
- SQLite writes: coalesced counter flushes at ≥30 s → ≤120 writes/h streaming; alarms/rows are event-driven and negligible — far under 100 k writes/day. Row reads: link-table load once per wake, negligible against 5 M/day.

**Measured cross-check:** the full test run (10,386 incoming messages, 53 HTTP, 3 alarms) billed to **576 requests** under the same model — the math is consistent end-to-end.

## 5. Decision / recommendation

The single-`AccountHub` design in [ADR-0002](../adr/0002-cloudflare-e2e-relay.md) is **validated** on workerd. No free-plan limitation breaks it. For [RLY/1](../specs/relay-v1.md) — applied by P0-A2:

1. **No wire changes.** Frame cap stays **65,536 bytes**; `error{too_large}` + drop (do **not** close the connection — measured survival proves the friendlier behavior works; `4400` stays reserved for malformed protocol per §9). Close codes `4401`/`4408`/`4409` behave as specified; reason string `replaced by newer connection` is fine as-is.
2. **§3 keepalive text — clarify implementation, not the wire.** The auto-response pair MUST be registered byte-exact: request `{"t":"ping"}`, response `{"t":"pong"}` (as §5 already shows). Ping interval stays **25 s** (a prior draft of this doc claimed 15 s — wrong; 25 s keeps a 35 s margin before the 60 s reconnect threshold). Document that auto-response traffic must not wake the object (measured: `ws_msg_in` delta 0).
3. **§3 add one sentence:** any abnormal client close (**1006**, i.e. relay restart/deploy/network drop) triggers jittered reconnect + cursor resume; clients must not distinguish “relay gone” from “network gone”. (Measured: killing `wrangler dev` produced exactly 1006/`wasClean=false`.)
4. **§8 host-offline alarm:** keep **120 000 ms** grace (a prior draft's 60 s is wrong). Implementation pattern confirmed: persist tasks in SQLite, one alarm at `min(due)`, `deleteAlarm()` on reconnect cancel — measured arm/cancel/fire with no false positives.
5. **§10 limits unchanged**; spike ran with `HOST_OFFLINE_ALERT_MS=5000` for observability only.
6. **Free-plan model confirmed:** streaming ≤7 msg/s coalesced costs ≈1.3 % of quota per hour (§4.9); P1-R1 should expose the same `billed` counters (20:1 of `ws_msg_in` + HTTP + alarms) as first-class metrics so quota drift is visible.
7. **Hibernate API pattern:** accept with `ctx.acceptWebSocket(server, [id])` (tag = endpoint id), keep `serializeAttachment` minimal (`endpointId, kind, nonce, connectedAt, authed…`), rebuild any caches on wake — measured survival across eviction.
8. **Spike deviations are spike-only, not spec changes:** HMAC-SHA256 demo auth instead of Ed25519 (fail-closed path still measured), ASCII ids ≤16 chars standing in for the 16-byte base32 payload, unauthenticated enroll routes, no rate limiting, no presence/push fan-out. P1-R1 implements the real Crypto/1/RLY/1 behavior; nothing here justifies weakening the spec.

## 6. Residual unknowns

- **Auto-response request billing:** pricing footnote 3 exempts auto-response from *duration*; whether those incoming pings also count toward the 20:1 request budget is not observable without a deployed account. Bound: 0–15 requests/h — immaterial either way (both fit §4.9). Listed as an open billing question for P1-R1's deploy.
- **Optional acceptance box skipped:** one deploy to the owner's Cloudflare account to confirm SQLite-backed DO availability on their free plan was **not performed — owner unavailable this session** (packet says to skip and say so). wrangler dev exercises the same DO API surface, but the entitlement check remains open.
- **Real edge vs loopback:** RTT numbers are Windows loopback through workerd; production adds WAN + edge latency on the same code path. Hibernation threshold (10 s) and 1006-on-deploy were measured on `wrangler dev` only; a production deploy should re-confirm with a post-release probe.
- **Soak duration:** zero-wake evidence covers the measured windows (50 pings/34 s, 15 s hibernation idle), not a multi-hour quiet period. A P1 soak should confirm `wakes` stays flat over hours with only 25 s pings.
- **Scale beyond two endpoints:** routing, replacement, and fan-out were measured with host + device (+ one replacing socket). `MAX_ENDPOINTS=32` and multi-device offline fan-out are untested.
- **Presence, push/FCM, tickets, rate limits:** out of P0-S3 scope; covered by later tasks/spec sections, untouched here.
