## 4. Results (each ×2; all 18 runs `ok:true`)

Evidence per run: `summary.json` (incl. `browserOutput`), `events.jsonl`, `control-log.json`.

### E1 — no browser connected

- Root listener **does** receive the request (`approval/enter`, `hasSignal:true`) before any terminal default.
- With **zero** remote-event clients, `next()` **parks** (zero deliveries). After `nextTimeoutMs` (4000 ms) the bridge logs `approval/next-resolved outcome:"p0-s2:next-timeout" timedOut:true`.
- Synthetic self-check waterfall that **registers its own terminal** settles immediately with `result:"unavailable"` — that terminal is **not** what a real zero-client `approval/request` hits.
- **Correction to ADR-0008 context:** zero-client does **not** fall through to the approval `unavailable` default; it hangs until someone answers or the turn aborts.

### E2 — one browser tab open (passive)

- Browser receives `waterfall approval/request` (card present on PC).
- Bridge still enters first (`approval/enter` before the passive client answers).
- Passive browser never posts an answer → `next()` again times out (`next-timeout` after ~4000 ms).
- Both surfaces hold the request; neither auto-resolves.

### E3a — phone answers first, withdrawal **(a) signal substitution** ✅ selected

Sequence in `events.jsonl` + browser:

1. `withdraw/signal-substituted`
2. `approval/claimed outcome:"allowed-once"`
3. `withdraw/signal-aborted`
4. `approval/pc-chain ok:false error:"… bridge answered first; withdrawing PC chain"`
5. Browser: `waterfall` then **`cancel`** for the same `eventId`

PC chain rejects **in ~60 ms** (not 4 s timeout). Parent turn is not aborted.

### E3b — phone answers first, withdrawal **(b) observe `approval/decided`**

- `approval/claimed` then `withdraw/decided-observe` note: *ui-approval does not subscribe `approval/decided`; expect stale card unless cancel arrives*.
- Browser: `waterfall` only — **no `cancel`**. Card stays until gateway teardown.
- `approval/pc-chain` → `timeout waiting for PC chain` (~4 s).
- **`approval/decided` is not in `API_REMOTE_FORWARDED_EVENTS`**; the scripted client never sees it. Stale-card limitation confirmed.

### E3c — phone answers first, withdrawal **(c) none**

- Same stale card and PC-chain timeout as E3b. Baseline.

### E4 — browser answers first

- Browser posts answer → HTTP 200 `{"ok":true}`.
- Bridge: `approval/next-resolved outcome:"allowed-once" ms:6–8` (observe mode returns GUI result).
- First-wins race: GUI answer cancels the phone side.

### E5 — request signal aborted (turn cancelled)

- `session/cancel` after 800 ms.
- Bridge: `approval/next-rejected error:"typert gateway: Remote event was cancelled"` (~625 ms).
- Browser: `waterfall` then **`cancel`**. Both sides tear down; no orphan pending.

### E6 — preview tool args by `callId`

| Path | Result |
|---|---|
| Live session / `snapshotEvents` | `preview/live found:true` — `{"note":"e6-preview","secret":"not-really"}` |
| `sessionController.inspect` | `preview/inspect found:true` — same args, `eventCount:19` |
| Missing session (static) | `session "session-missing" not found` (fail closed) |

Both paths agree on `args` for the live `callId`. Prefer live Session for zero-overhead mid-turn reads; `inspect` for resume/history.

### Self-check (×2)

```json
{"kind":"selfcheck","order":["bridge-prepend","sentinel-ordinary","terminal"],"prependFirst":true,"result":"unavailable"}
```

Bridge prepend runs first; ordinary sentinel second; self-check terminal last.

## 5. Decision / recommendation

**Selected withdrawal mechanism (ADR-0008):** before calling `next()`, replace `req.signal` with `AbortSignal.any([original, derived])`. When the phone wins, abort `derived` → gateway `cancelRemoteEvent` → browser card removed; parent turn signal stays live.

Do **not** rely on `approval/decided` to clear the PC card (not forwarded to remote clients). Document the stale-card gap for an upstream proposal if signal substitution ever cannot be applied.

**Recommended AnswerBridge algorithm:**

```ts
ctx.on('approval/request', async (req, next) => {
  if (deviceRegistry.pairedCount === 0) return next()

  const derived = new AbortController()
  const signal = req.signal
    ? AbortSignal.any([req.signal, derived.signal])
    : derived.signal

  const gui = next({ ...req, signal }).catch((e) => ({ kind: 'gui-error', e }))
  const phone = pendingManager.create({ /* preview, argsDigest, risk */ })

  const winner = await raceFirst([phone, gui, abort(req.signal), timeout(approvalTimeoutMs)])

  if (winner.side === 'phone') {
    derived.abort()          // withdraw browser card
    return winner.decision
  }
  pendingManager.cancel(approvalId, 'resolved_by_gui')
  return winner.decision     // phone side withdrawn
}, { prepend: true })
```

Same shape for `user-questions/request` (plugin registers both; question path not driven end-to-end in this spike — see residual).

**Startup self-check:** synthetic waterfall with bridge prepend + ordinary sentinel + terminal; assert `prependFirst === true` or fail closed at load.

## 6. Residual unknowns

1. **`user-questions/request` end-to-end:** listener and answer/withdraw code paths exist in the spike (`question/enter`, etc.) but the mock LLM experiments drove only `approval/request`. Re-verify once with `ask_user_question` before P3-H1.
2. **Real dsh GUI (browser JS) vs scripted mux client:** cancel frames prove the gateway withdraws the stream; a real `ui-approval` card still needs one manual screenshot on a desktop browser when convenient (scripted client cannot render DOM).
3. **Zero-client parking vs upstream intent:** if upstream intended a terminal `unavailable` on zero clients, that differs from observed `startRemoteEvent` behavior — track as an upstream question, do not edit `docs/upstream/dsh-integration.md` from this spike.

## 7. Implications (applied by Integrator / P0-A2)

- ADR-0008 status finalized; mechanism = derived AbortSignal substitution; remove “approval/decided clears UI” as a hard dependency.
- ADR-0008 context sentence about zero-client → terminal `unavailable` must be corrected (parking observed).
- Production AnswerBridge (P3-H1) must race phone vs `next()` with a timeout; cannot assume `next()` settles alone.
