# Crypto/1 — Identities, pairing, secure channel, signatures

Status: **v1-draft** (frozen by P0-A1; changes require the contract-change process in [AGENTS.md](../../AGENTS.md#6-contract-change-process)).
Implementations: TypeScript `@remora/crypto` (host, testkit), Kotlin `:core:crypto` + `:core:security` (Android), relay auth verification in `apps/relay`.
Every construction below has vectors in `conformance/vectors/crypto/`; both implementations MUST pass them.

## 1. Primitives and libraries

| Primitive | Standard | TypeScript | Kotlin / Android | Relay (Workers) |
|---|---|---|---|---|
| X25519 | RFC 7748 | `@noble/curves/ed25519` `x25519` | BouncyCastle `X25519Agreement` | — |
| Ed25519 | RFC 8032 | `@noble/curves/ed25519` `ed25519` | BouncyCastle `Ed25519Signer` | WebCrypto `Ed25519` verify |
| ChaCha20-Poly1305 (IETF, 96-bit nonce) | RFC 8439 | `@noble/ciphers/chacha` | BouncyCastle `ChaCha20Poly1305` | — |
| SHA-256, HMAC-SHA256, HKDF-SHA256 | FIPS 180-4, RFC 2104, RFC 5869 | `@noble/hashes` | BouncyCastle / JCA | WebCrypto |
| ECDSA P-256 with SHA-256 | FIPS 186-5 | `@noble/curves/p256` (verify only) | Android Keystore (sign only) | — |
| CSPRNG | — | `crypto.getRandomValues` | `SecureRandom` | `crypto.getRandomValues` |

Rules: no home-made primitives; constant-time comparisons for secrets and MACs; secrets never logged, never placed in exceptions, zeroized best-effort after use (`fill(0)`).

Encodings: **b64u** = base64url without padding (RFC 4648 §5). **base32** = RFC 4648 alphabet, lowercase, no padding. Byte concatenation is `‖`; `0x00` is a single zero byte used as a separator; strings are UTF-8.

## 2. Endpoint identities

```
endpointId = prefix ‖ base32( SHA-256( "remora/1 endpoint-id" ‖ 0x00 ‖ relayPub )[0..16] )
prefix     = "h_" for hosts, "d_" for devices          → 28 characters total
```

`relayPub` is the endpoint's 32-byte Ed25519 public key. The relay recomputes the id at enrollment and on every authentication; the host recomputes a device id from the `relayPub` inside pairing msg1.

## 3. Key inventory

| Key / secret | Size | Generated by | Stored at | Lifetime |
|---|---|---|---|---|
| HostNoiseKey (X25519) | 32 B | host, first start | dsh credentials record `remora/host-identity` | host lifetime (rotation = re-pair all devices) |
| HostRelayKey (Ed25519) | 32 B seed | host, first start | same record | host lifetime |
| DeviceNoiseKey (X25519) | 32 B | phone, per host pairing | Tink keyset (Keystore-wrapped) | until unpair |
| DeviceRelayKey (Ed25519) | 32 B seed | phone, per host pairing | Tink keyset | until unpair |
| DeviceApprovalKey (EC P-256) | — | phone, per host pairing | Android Keystore, non-exportable, StrongBox when available, per-use biometric auth, invalidated by new biometric enrollment | until unpair or invalidation |
| devicePsk | 32 B | host at `pair.complete` | host: credentials record `remora/device/<deviceId>`; phone: Tink | until unpair |
| pushKey | 32 B | host at `pair.complete` | same as devicePsk | until unpair |
| pairingSecret | 32 B | host, per pairing attempt | memory only (and the QR) | ≤ 10 min, single use |
| Enrollment ticket | 32 B | relay | relay stores SHA-256(ticket) | ≤ 10 min, single use |
| REMORA_ENROLL_SECRET | ≥ 32 B random | owner | Cloudflare secret; dsh credentials key `REMORA_RELAY_ENROLL_SECRET` | until rotated |

Each (host, device) pair has independent device keys: pairing the same phone with two PCs produces two unlinkable device identities.

## 4. Relay authentication

On every WebSocket connection the relay sends a fresh 32-byte `nonce` (see [RLY/1 §3](relay-v1.md#3-connection-and-authentication)). The endpoint signs:

```
authMessage = "remora/1 relay-auth" ‖ 0x00 ‖ relayOrigin ‖ 0x00 ‖ kind ‖ 0x00 ‖ endpointId ‖ 0x00 ‖ nonce
signature   = Ed25519.sign(RelayKey, authMessage)
```

`relayOrigin` is the exact origin string the client connected to (e.g. `https://remora-relay.example.workers.dev`), `kind` is `host` or `device`. The relay verifies with the stored `relay_pub`, checks the endpoint is not revoked, and that the id derives from the key. Binding the origin and nonce prevents replay across connections and deployments.

## 5. Pairing

### 5.1 QR payload

```
remora://pair?v=1&r=<relayOrigin>&h=<hostId>&k=<b64u HostNoiseKey.pub>&t=<b64u ticket>&s=<b64u pairingSecret>&n=<hostName>&x=<expiry unix seconds>
```

All values are percent-encoded; `hostName` ≤ 40 characters. The app MUST reject `v≠1`, an expired `x`, a non-`https` relay origin (except `http://127.0.0.1` / `http://10.0.2.2` in debug builds), and malformed keys.

### 5.2 Pairing PSK

```
pairPsk = HKDF-SHA256(ikm = pairingSecret, salt = "remora/1", info = "pair-psk" ‖ 0x00 ‖ hostId, L = 32)
```

### 5.3 Pairing handshake

1. The phone enrolls at the relay with the ticket ([RLY/1 §4.2](relay-v1.md#42-device-enrollment)) and authenticates its socket.
2. It runs the secure channel handshake (§6) with `purpose = "pair"`, `psk = pairPsk`, the responder static key pinned to `k` from the QR.
3. **msg1 payload** (JSON, encrypted by Noise):

```json
{ "v": 1, "purpose": "pair", "deviceId": "d_…", "relayPub": "<b64u>", "name": "Pixel 8",
  "platform": "android", "approvalPub": "<b64u SPKI DER P-256>", "attestation": ["<b64u cert>", "…"],
  "app": { "version": "0.1.0" } }
```

4. The host MUST verify: a pairing attempt with this ticket is open and unexpired; decryption succeeded (proves `pairPsk`); `deviceId` derives from `relayPub` (§2); the relay frame's source id equals `deviceId`; `approvalPub` parses as an uncompressed P-256 point. `attestation` is optional in v1: the host records whether it was present and, if it verifies, whether the key is hardware-backed.
5. **msg2 payload**: `{ "v": 1, "hostId": "h_…", "hostName": "DESKTOP-OLSI", "versions": { "remora": "0.1.0", "dsh": "0.1.5-rc.3", "rcp": [1] } }`.
6. **SAS**: both sides compute

```
sas = uint32_be( HMAC-SHA256(key = handshakeHash, msg = "remora/1 sas")[0..4] ) mod 1 000 000
```

rendered as six digits with leading zeros, grouped `482 193`. The phone shows it; the host shows it next to the device name with **Confirm** / **Reject**. Pairing MUST NOT complete without an explicit confirmation on the PC.

7. On confirmation the host generates `devicePsk` and `pushKey` (CSPRNG), stores the device record, and sends RCP `pair.complete` (see [RCP/1 §7](rcp-v1.md#7-pairing-and-devices)) over the transport, then closes the channel. On rejection or after 2 minutes: `pair.rejected`, relay `endpoint.revoke`, all pairing state discarded. A ticket and pairing secret are never reused.

## 6. Secure channel SC/1

- Protocol name: **`Noise_IKpsk2_25519_ChaChaPoly_SHA256`** (Noise rev. 34). Initiator = device, responder = host. The initiator knows the responder static key from pairing (`k`), the responder learns and checks the initiator static key.
- **Prologue:** `"remora/1" ‖ 0x00 ‖ purpose ‖ 0x00 ‖ hostId ‖ 0x00 ‖ deviceId`, `purpose ∈ {"pair","session"}`. A relay that splices messages between contexts causes a handshake failure.
- **PSK:** `pairPsk` for `pair`; `devicePsk` for `session`.
- **Session admission (host):** after reading msg1 the host MUST look up the initiator static key; it MUST equal the stored `DeviceNoiseKey.pub` for the device whose id equals the relay source id, and that device MUST NOT be revoked. Otherwise: drop, no response, count as an auth failure.
- **Session msg1 payload:** `{ "v": 1, "purpose": "session", "app": { "version": "…" } }`; **msg2 payload:** `{ "v": 1, "time": <host ms> }`.
- **Records inside RLY/1 data frames** (first plaintext byte of the L1 payload):

| Byte | Record | Contents |
|---|---|---|
| `0x01` | handshake msg1 | Noise message |
| `0x02` | handshake msg2 | Noise message |
| `0x03` | transport | Noise transport ciphertext of exactly one RCP message (plaintext ≤ 49,152 B) |

- **Channel id:** the initiator picks a random non-zero u32 per handshake and uses it in the L1 `channel` field; frames for unknown or superseded channels are dropped.
- **Failure:** any decryption failure, out-of-order nonce, or oversize record closes the channel; the initiator reconnects with a new handshake. There is no resynchronization.
- **Rekey:** a new handshake at every reconnect and at least every 24 h or 2^20 transport messages per direction, whichever comes first.
- **Handshake flooding:** the host keeps at most 4 half-open handshakes per device id and 32 total; excess msg1 frames are dropped.

## 7. Approval signatures

Used when an approval's `risk` is `high`, or for every approval when the host policy is `approvalBiometric: all`, and for permission escalations requested from the phone.

**Preview digest.** The host sends `preview.text` (human summary) and `preview.json` (raw JSON of the truncated arguments, as a string). Both sides compute

```
argsDigest = hex_lower( SHA-256( UTF-8(preview.text) ‖ 0x00 ‖ UTF-8(preview.json) ) )
```

The phone MUST recompute it from the bytes it displays and refuse to sign on mismatch.

**Canonical message** (UTF-8 lines joined by `\n`, no trailing newline):

```
remora/1 approval
<hostId>
<deviceId>
<approvalId>
<sessionId>
<callId, or "-" when absent>
<toolName>
<argsDigest>
<outcome: allowed-once | rejected>
<issuedAt: decimal milliseconds since the Unix epoch>
```

**Signature:** ECDSA P-256 with SHA-256 over the message bytes using `DeviceApprovalKey` inside a `BiometricPrompt` `CryptoObject` (`Signature("SHA256withECDSA")`), DER-encoded, sent as b64u.

**Verification (host):** P-256 verify with the stored `approvalPub`, DER format, **high-S signatures accepted** (Android does not normalize `s`; with `@noble/curves` pass `{ prehash: true, lowS: false, format: 'der' }`). Then check pending state, digest equality, `|issuedAt − hostNow| ≤ 5 min`, and single use of `approvalId`.

Rejections are signed too when a signature is required: a forged "reject" is harmless, but symmetric handling keeps the code path simple.

## 8. Push payload encryption

```
nonce = 12 random bytes
aad   = "remora/1 push" ‖ 0x00 ‖ hostId ‖ 0x00 ‖ deviceId
ct    = b64u( nonce ‖ ChaCha20-Poly1305.encrypt(key = pushKey, nonce, plaintext, aad) )
```

Plaintext is JSON ≤ 2,048 bytes:

```json
{ "v": 1, "kind": "approval", "at": 1790000000000, "sessionId": "…", "pendingId": "…",
  "title": "Approval needed · ds", "body": "bash: pnpm test" }
```

`kind ∈ {approval, question, turn_done, turn_error}`. The relay-generated `host_offline` push carries no ciphertext; the app renders it from its own host record. Random 96-bit nonces are safe far beyond Remora's volume (≪ 2^32 messages per key).

## 9. Storage requirements

- **Host:** secrets only through `ctx.credentials` records; never in `cordis.patch.yml`, logs, the storage domain, or exceptions.
- **Phone:** Tink `AndroidKeysetManager` with master key `android-keystore://remora_master_v1`; approval keys alias `remora_approval_<hostId>`; `android:allowBackup="false"` and data-extraction rules excluding all app data; keys deleted on unpair.
- **Relay:** stores public keys, hashed tickets, FCM tokens. Never private keys, PSKs, push keys, or payloads.

## 10. Revocation and rotation

| Event | Action |
|---|---|
| Device revoked (PC or self) | host deletes device record + credentials record (authoritative), closes channel, sends `endpoint.revoke`; relay marks revoked, closes socket, clears FCM token |
| Biometric enrollment changed on phone | approval key invalidated; app generates a new one and sends `devices.rotateApprovalKey` which requires SAS-style confirmation on the PC |
| Relay enroll secret rotated | update Cloudflare secret and dsh credential; existing endpoints unaffected |
| Host key compromise | re-install host identity (delete record), re-enroll, re-pair all devices (v1 has no in-place rotation) |
