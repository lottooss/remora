## Summary

The host can now survive the real-dsh startup race: on a freshly booted dsh the
first gateway calls reject with `code === 'gateway/service-unavailable'` while
`sessionController` is still starting — the exact failure recorded in
`packages/host/test/fixtures/dsh-0.1.5-rc.3/report.json`
(`typert gateway: session/list: active Service "sessionController" is unavailable`).
A new `RetryingGateway` class wraps the raw dsh `ctx.typertGateway` and makes
`invoke` and `stream` retry exactly that error code every 250 ms, up to a
configurable 30 s deadline (constructor option), honoring the caller's
AbortSignal; every other error propagates on first occurrence with the original
error object. The retry pattern is the one proven by the P0-S1 spike
(`spikes/p0-s1-dsh-adapter/src/index.js`, `invokeReady`), made configurable,
abortable, and deterministic-testable via injected `clock`/`sleep`.

## Known limitations / follow-ups

- `RetryingGateway` is not yet constructed anywhere in production: wiring it
  around `ctx.typertGateway` inside `apply()` belongs to `packages/host/src/index.ts`,
  which is P7-H1's packet (currently being reworked by another worker); touching it
  here would have violated `owned_paths`. Until that wiring lands, dsh calls do not
  get the retry behavior in production.
- The `stream` wrapper retries opening the stream only; errors raised while
  iterating an established stream are the stream consumer's concern (documented on
  the class).
