## Summary

The bridge uses upstream approval/question types, stops its startup probe before
ordinary listeners, and derives approval previews from recorded tool arguments.
Review found that the first implementation detached the real Session method,
classified arguments absent from real approval requests, and never supplied the
Policy Guard from `apply()`. The follow-up preserves the Session receiver,
classifies full journal arguments before truncation, requires high-risk
authorization for invalid metadata, and wires the configured policy and timeout
through the production entry point. A failed startup self-check now refuses
startup before credentials or relay resources are created.

## Known limitations / follow-ups

- The Integrator identified an existing cross-language approval contract mismatch:
  TypeScript, Kotlin, and Crypto/1 describe different digest/canonical-message
  behavior. This PR preserves the crypto implementation. Its preview digest
  assertions use the current TypeScript helper and do not prove Crypto/1 or
  Android parity; that needs a separate contract-change decision and joint fix.
- This worker did not independently reproduce the original fixture recording.
  The original fixtures are replayed; the new receiver tests use the actual
  pinned Session implementation instead of an arrow-function journal fake.
- No phone, cloud, Firebase, or deployed-relay acceptance is claimed. These remain
  OWNER-PENDING under their own packets.
- Formal verification must use the independent fresh-context verifier required
  by SWARM.md; worker checks are not `VERIFIER: PASS`.
