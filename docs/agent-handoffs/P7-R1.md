# Handoff: P7-R1 — Relay push test is order-dependent (host-offline alarm leaks into the next test)

- **Role:** relay
- **Agent:** Claude Code (Opus 5.5), `remora-worker`
- **Date:** 2026-10-01
- **Branch / PR:** `task/P7-R1-relay-push-test` / [#87](https://github.com/lottooss/remora/pull/87)
- **Commits:** `155a02e` (red) · `4fd6fe6` (green)

## Summary

`apps/relay/test/push.test.ts` no longer depends on real time. The file now uses the RLY/1 §8 host-offline delay (120 s, far longer than the file runs), so no host-offline alarm fires on its own. Every firing is explicit: `runAlarmAt(hub, at)` sets the clock with `vi.setSystemTime` (the Durable Object shares `Date` with the tests in this isolate) and calls `runDurableObjectAlarm`. `disconnectHost()` closes a host socket and waits, up to a 2 s deadline, until the relay has stored the offline task and armed the alarm, so a close is never processed inside a later test. `beforeEach` fires any alarm an earlier test left pending before it resets the captured FCM requests. Each test now asserts on the exact requests it produces. The alarm test still asserts that exactly one `host_offline` push is sent and that it is sent only after the delay. `apps/relay/src/**` is unchanged.

## Red: deterministic reproduction (commit `155a02e`)

The red commit adds the explicit alarm control. At the start of the push test, it also fires every host-offline alarm that is still pending. This is the timing the CI flake hit: after `beforeEach` has reset the captures and before the host reconnects and cancels the task. In this commit, the alarm armed by `beforeAll`'s host disconnect is still pending. The device registered its token in the previous test, so the alarm's `host_offline` push lands inside the push test, and the original assertion fails:

```text
$ pnpm -F @remora/relay test            # exit 1
 FAIL  test/push.test.ts > Relay push dispatch + host-offline alarm (RLY/1 §8, P5-R1) > dispatches push message from host to device with byte-identical ciphertext
AssertionError: expected 2 to be 1 // Object.is equality
 ❯ test/push.test.ts:303:40
    303|     expect(capturedFcmRequests.length).toBe(1)
      Tests  1 failed | 17 passed (18)
```

The failure is deterministic: 10 local runs of the red commit all failed exactly this way (`red-as-predicted: 10/10`). I added a one-off log line in a throwaway copy of the red file (deleted afterwards) to show that the extra request is the leaked alert:

```text
CAPTURED [{"v":"1","h":"h_ptm5…","k":"host_offline"},{"v":"1","h":"h_ptm5…","ct":"E2E_CIPHERTEXT_1234567890_…"}]
```

## Deviations from the packet

None. The packet allows either approach, and this uses both: the alarm is driven explicitly with `runDurableObjectAlarm`, and each test asserts only on its own requests. The test delay is now the spec's 120 s instead of 100 ms. The alarm test proves "only after the delay" with the clock set 1 ms before the delay elapses (no push), then after it (exactly one push), then again later (no second push and no alarm left).

## Known limitations / follow-ups

- The tests in the file still share enrollment state in order. The push test relies on the token that the first test registers; this is by design and not part of this packet. Only the alarm leak was fixed.
- I noticed this in the relay source and did not change it, because it is out of scope. `cancelOfflineTask()` in `apps/relay/src/account-hub.ts` deletes the DO alarm whenever no offline task remains, even if an auth-timeout alarm was armed for another socket that is still unauthenticated. That socket is then only closed by a later alarm. The Integrator may want a packet for it.
