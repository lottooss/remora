## Summary

The host now registers exactly the device-callable RCP/1 method set (`RCP_METHODS`, the reconciled 36-method list from P7-C1): `devices.self`, `devices.unpair`, and `devices.rotateApprovalKey` are implemented and the off-spec extras `sessions.get`, `files.readBytes`, `diffs.get`, `diffs.hunk` are gone. Unpair goes through the P7-H4 registry revocation path (one atomic whole-record credentials write that drops the device's PSK, push key, and preferences) and closes the device's channels after the `{ ok: true }` reply; key rotation answers `pending_pc_confirmation` and the new key becomes active only after a PC confirms on the management page (new Confirm/Reject routes; crypto-v1.md §10). A parity test asserts after the real plugin `apply()` that the registered set equals `RCP_METHODS`.

### What the tests prove (all through real code, no mock of the unit under test)

- **Parity** — mounting the real plugin via `ctx.plugin(host, …)` on a real Cordis context, `RcpServer.registeredMethodNames()` equals `RCP_METHODS` exactly (sorted set equality, both directions).
- **devices.self** — returns `{ id, name, pairedAt, approvalKey: { hardwareBacked: null } }` of the CALLING device (self-only; `hardwareBacked` is unknowable from the host, RCP/1 §7 allows null); fail-closed `forbidden` for an unknown or revoked caller.
- **devices.unpair** — replies `{ ok: true }`; the credentials record afterwards has the device `revoked: true` with `devicePsk`/`pushKey`/notify prefs dropped by the same write; a second unpair is refused `forbidden`; key material never appears in any captured log record. Over a **real Noise IKpsk2 channel** (`test/rcp/devices-channel.test.ts`: real `ChannelManager` + real `RcpServer` + real `PersistentDeviceRegistry`, revocation wired exactly like `apply()`), the reply frame decrypts to `{ ok: true }` and only then `hasSession`/`hasDeviceSession` turn false — a follow-up request on the same channel gets no reply; the relay revoke was scheduled for after the reply.
- **devices.rotateApprovalKey** — answers `{ status: 'pending_pc_confirmation' }`; the stored record keeps the OLD approval public key while pending; the management Confirm route activates the new key (visible in the stored record via `waitFor`) and the page's pending list empties; Reject leaves the old key active and a late confirm answers 409; confirm with nothing pending → 409; key-shape validation (64-byte, non-0x04 prefix, non-base64url → `invalid_params`); same-`requestId` retry is idempotent; a different `requestId` while pending → `conflict`.

## Known limitations / follow-ups

- `@remora/protocol` still exports the now consumer-less `SessionsGet*`/`FilesReadBytes*`/`DiffsGet*`/`DiffsHunk*` schema groups (protocol is not in this packet's `owned_paths`; their annotations say "stay exported for that handler" until P7-H7 — that handler removal is what this PR does). Suggest the Integrator/protocol-crypto delete them via the §6 contract process.
- `FilesAdapter.readBytes` and `FilesAdapter.diffsHunk` (`packages/host/src/adapter/files.ts`, not owned) lost their last RCP callers; the adapter test still exercises `readBytes` directly. Adapter cleanup can follow in a host-role follow-up.
- `devices.unpair` does not add a `requestId` dedup cache: after the first unpair the device's channels are closed and the channel layer refuses revoked devices at handshake, so a retry cannot reach the handler; a same-channel duplicate is refused `forbidden` (fail closed, no double execution).
- The `pack.test.ts` afterAll (`fs.rmSync` of the npm temp dir) timed out twice on this Windows machine during development while the 5 assertions passed, and passed on reruns (including on pristine main) — a local file-lock flake, not touched by this diff; CI is the evidence of record.
