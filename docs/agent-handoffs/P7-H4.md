## Summary

The paired devices and the per-device notification preferences now persist in the dsh credentials record `remora/devices` — one grant record holding every device entry (endpoint id, name, Noise public key, revoked flag, approval public key and, for non-revoked devices, the 32-byte `devicePsk` and `pushKey`) plus the per-device notify preferences. `loadPersistentDeviceRegistry(credentials)` (packages/host/src/devices/persistent-registry.ts) loads it on every start, creates it atomically on first start (the P7-H2 `loadOrCreateHostIdentity` pattern), and fails closed with `DeviceRegistryRecordError` on a record it cannot parse instead of starting over empty (which would silently unpair every phone). Every mutation is written as a whole-record `modifyRecord` write on a serialized queue, so `revokeDevice` deletes the device's secrets and preferences in the very write that revokes it (crypto-v1.md §10) and there is no committed state where a revoked device's secrets outlive the revocation. `apply()` wires the loaded registry everywhere the old memory-only one was used, and the same instance is the `NotifyPrefsStore` (preferences share the record and its write queue). Secret material never appears in logs, error messages, or the console bridge (crypto-v1.md §9, AGENTS.md §1.8).

## Acceptance criteria

- [x] **Unit tests: pair → re-create registry from the same credentials store → device still admitted; revoke survives restart.**
  Evidence: `packages/host/test/devices/persistent-registry.test.ts` (11 tests, green locally and in CI run 37022858643). The first test pairs a device into the store via `addDevice`, reloads the registry from the same credentials store with `loadPersistentDeviceRegistry`, and asserts the device is returned by `getDeviceById`/`getDeviceByNoiseKey` (the session-admission lookup, crypto-v1.md §6) with byte-identical `noisePublicKey`/`devicePsk`/`pushKey` and `revoked: false`. The revocation test asserts the stored record entry has `revoked: true` and **no** `devicePsk`/`pushKey` after the revocation write, and that a reload still reports the device as revoked. Further tests cover: prefs survival across a reload, prefs dropped in the revocation write, rename persistence, `onWriteError` reporting, fail-closed parsing of seven corrupt-record shapes (record left untouched in every case), no key material in rejection messages, revoked entries stored without secrets, and adoption of the create-race winner.

  The packet offered "extend tests/real-dsh OR add a host apply test"; per the Integrator notes the apply-test route was chosen — `tests/real-dsh/**` is a protected path this packet does not own. ## Deviations from the packet

- **File-path/memory constructor modes kept (tests only).** The packet allows "Remove the file-path mode or keep it for tests only"; the modes are kept because `packages/host/test/pairing.test.ts` (not in this packet's `owned_paths`) constructs `new PersistentDeviceRegistry(filePath)` and `new PersistentDeviceRegistry()`. The file/memory modes are documented as tests-only in the class JSDoc; production (`apply()`) only ever gets the credentials-backed instance from the loader.
- **Notify prefs live in the same `remora/devices` record** (the packet allows "the same record or `remora/notify-prefs`"); one record keeps the revocation's "delete secrets and prefs in one write" guarantee trivially atomic.
- **Stricter than the old in-memory registries:** the credentials-backed `addDevice` also validates `pushKey` length and (credentials mode only) the `d_` + 26 base32 endpoint-id shape, so a malformed device can never be written into a record that would then fail closed on the next boot. Production pairing derives ids exactly in that shape (`encodeBase32` of the relay public key), and the legacy file/memory modes used by the pairing tests keep the old validation.

## Known limitations / follow-ups

- `lastSeenAt` updates made by the channel manager on a returned record are persisted only with the next registry write (pairing, revocation, prefs, rename). Correctness-relevant state is always written immediately; a follow-up could enqueue a coalesced `lastSeenAt` flush (not required by the packet).
- Two registry instances over one credentials store (only possible in tests today) write whole-record snapshots; last writer wins. One host process runs per dsh profile, and the write queue serializes mutations within a process.
- The `remora/devices` payload version is 1; a future wire change goes through the contract-change process (AGENTS.md §6).
