## Goal

Implement [ADR-0008](../adr/0008-answer-bridge-race.md) with the mechanism selected in P0-S2: phones and the PC GUI can both answer approvals and questions, the first valid answer wins, the loser is withdrawn, and being away from the PC never fails a request early.

## Inputs

ADR-0008, `docs/spikes/P0-S2.md`, blueprint §8.6, §11.4–§11.5, RCP/1 §8, Crypto/1 §7.

## Deliverables

- `interaction/dsh-waterfalls.ts`: prepend root listeners for `approval/request` and `user-questions/request`; transparent `return next()` when no device is paired.
- `interaction/pending.ts`: pending registry (ids, previews via callId lookup, `argsDigest`, expiry, single-use, resolution fan-out).
- `interaction/race.ts`: phone vs `next()` vs signal vs timeout; ignore `unavailable`/`NO_PROVIDER` from `next()` while a device is paired; withdrawal per P0-S2.
- RCP: `interaction.follow` (baseline + deltas), `approvals.answer`, `questions.answer` (signature enforcement delegated to the Policy Guard interface from P3-H2; stub allows `normal` risk until P3-H2 lands).
- Startup self-check that the bridge listener is first; log and disable with a loud error if not.
- Tests with mock waterfalls and e2e with the mock LLM: phone-first, PC-first, no-GUI, cancel, timeout, duplicate answer, answer after revoke, plan-review question.

## Acceptance

- [ ] e2e: with no browser connected, an approval waits for the phone and succeeds.
- [ ] e2e: with a browser connected (Playwright-driven dsh GUI or the P0-S2 harness), whichever side answers first wins and the other side stops showing the request (or the documented limitation holds).
- [ ] Each pending id accepts exactly one answer.

## Constraints

- Waterfall listeners call `next()` exactly once when delegating; never block the dsh event loop.

## Stop and report

- dsh behavior differs from the P0-S2 findings in the pinned version.

pnpm -F @remora/host test && pnpm test:e2e -t interaction
